# Operations & Cutover

This is the **Operations** phase. Validation has proven equivalence; now plan the move to
production safely, with a way back. Mirrors AI-DLC Operations: deploy and monitor from
accumulated context, human signs off.

## Inputs
- Approved validation results (`03-validation/equivalence-report.md` +
  `03-validation/reconcile_report.yaml`)
- Conversion log and migration plan (for scope and known caveats)
- `connections.yaml`, `migration-config.yaml`
- The pair's playbook operations chapters (read the chapter `_index.md`, then only the files
  the plan needs), under `skills/<pair>-playbook/references/`:

  | Need | Chapter / file |
  |---|---|
  | Target version facts, support dates, platform defaults | `target-baseline-*.md` (PostgreSQL pairs: `oracle-to-postgresql-playbook/references/target-baseline-aurora-postgresql-18.md`; MySQL pairs: `oracle-to-mysql-playbook/references/target-baseline-aurora-mysql.md`) |
  | CDC / AWS DMS cutover | `tools/aws-dms.md` |
  | Connection switch, pooling, failover | `tools/rds-proxy.md`; `ha-dr/` |
  | Backups, snapshots, point of no return, rollback | `ha-dr/` |
  | Parameter groups and session settings to carry over | `configuration/` |
  | Post-cutover monitoring | `monitoring/` (Oracle pairs) or `management/monitoring.md` (SQL Server pairs); `performance-tuning/` |

  Cite the files you used in each generated document, as the construction phase does.

## Required disclaimer on every generated artifact
Every document produced in this phase — the cutover runbook, rollback plan, monitoring
checklist, and any other operational guide — **MUST begin with the disclaimer block below,
verbatim, as the first content in the file.** Do not omit or summarize it. These are
AI-generated operational plans for high-risk, production-facing actions; the human operator
owns validating them.

```markdown
> ⚠️ **AI-GENERATED — VALIDATE BEFORE USE.** This document was generated by the dbmig-aidlc
> AI-DLC framework from this migration's context. It is a **starting point, not an
> authoritative runbook.** Every step — commands, ordering, timings, rollback triggers,
> capacity and monitoring thresholds — must be **reviewed, adapted to your environment, and
> rehearsed in a non-production environment** before any production use. **You are responsible
> for validating the correctness, completeness, and safety of this plan before executing it.**
> This toolkit is intended for **non-production use**; production cutovers should be run by
> qualified personnel using your organization's change-management process.
```

## Step 1 — Cutover strategy
Pick and document the approach with the user:
- **Big-bang (downtime)**: quiesce source, final data sync, switch app, validate, open.
  Simplest; needs a maintenance window.
- **Minimal-downtime (CDC)**: bulk load + AWS DMS change data capture to keep the target in
  sync, then a short switchover. For large/24x7 systems. See the playbook
  `<pair>-playbook/references/tools/aws-dms.md` for CDC setup (substitute the active engine
  pair).

Framework one-time loads (`dbmig migrate-data`) are for dev/test only — production data movement
should use AWS DMS.

## Step 2 — Cutover runbook
Write `04-operations/cutover-runbook.md` as an ordered, time-estimated checklist:
1. Pre-cutover: final schema diff, target capacity check, backups/snapshots, freeze changes.
2. Data: final sync / DMS cutover, then **identity/sequence reset** — generated, not
   hand-written (see below).
3. Application: connection-string / driver switch (note JDBC/ODBC differences), feature flags.
4. Smoke tests: run the validation suite's critical queries against production target.
5. Open to traffic; monitor.
Include owner and rollback trigger for each step.

**Identity/sequence step — generate it from the catalog.** Do not write a templated
`setval(<seq>, COALESCE(MAX(id),1))` step with `<t>` placeholders: it touches the wrong set of
tables and makes an empty table's first id 2. Instead run (dry-run, read-only):
```bash
./dbmig reset-identity --schema <S> --project <P>
```
It reads the target catalog, lists **exactly** the tables with an identity/serial/
AUTO_INCREMENT column (tables without one are skipped), shows `MAX(id)` vs the next value
per column, and lists **standalone sequences** on both sides (not covered — set them to the
source value at cutover). It writes `04-operations/identity-reset-<S>.md`: paste/link that
file as the runbook step. At cutover the step is the same command with `--apply` (a gated
write to the target) — it sets each counter so `next = MAX(id)+1` (or START on an empty
table) and re-verifies, exiting non-zero if any column is not safe.

## Step 3 — Rollback plan
Write `04-operations/rollback-plan.md` (required if `migration-config.yaml
cutover.require_rollback_plan` is true):
- Point of no return and the decision criteria to roll back.
- How to revert app connections to the source.
- Data divergence handling (writes that landed on the target after cutover).
- Keep the source intact and reachable until a defined soak period passes.

## Step 4 — Monitoring
Write `04-operations/monitoring.md`: post-cutover checks for the first hours/days —
error rates, slow queries (PostgreSQL `pg_stat_statements`; MySQL slow query log and the
`sys` schema — `performance_schema` is OFF by default on Aurora MySQL), connection counts,
replication/CDC lag, autovacuum/bloat (PostgreSQL) or InnoDB history length (MySQL), and the
app-level KPIs that prove correctness. Use CloudWatch Database Insights (Performance Insights
reaches end of life on 2026-07-31). Take the specifics from the monitoring and
performance-tuning files listed under Inputs.

## Gate
Present the runbook, rollback plan, and monitoring checklist. **Stop at the gate: "Approve
the cutover & rollback plan?"** Cutover execution itself is a high-risk, production action —
only proceed under explicit user direction, step by step, never unattended.

## Safety
- Production cutover and data movement are high-risk. Confirm each destructive/irreversible
  step. Never drop or truncate source data. Verify backups exist before the point of no
  return.
