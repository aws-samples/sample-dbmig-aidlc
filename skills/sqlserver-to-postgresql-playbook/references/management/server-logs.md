## SQL Server

SQL Server logs system and user-generated events to the *SQL Server Error Log* and the *Windows Application Log* (recovery, kernel, security, maintenance, and general server messages). The Windows Application Log holds events from all Windows applications, including SQL Server and SQL Server Agent.

The SSMS Log Viewer unifies all logs into a single view (logs can also be opened in any text editor). Admins use the error log to confirm process completion (backups, batches) and investigate runtime errors. To view logs in SSMS: Object Explorer → **Management** → **SQL Server Logs** → choose the current log.

Common error codes:

| Error code | Error message |
|---|---|
| 1105 | Couldn't allocate space. |
| 3041 | Backup failed. |
| 9002 | Transaction log full. |
| 14151 | Replication agent failed. |
| 17053 | Operating system error. |
| 18452 | Login failed. |
| 9003 | Possible database corruption. |

## PostgreSQL

Aurora PostgreSQL gives administrators access to the PostgreSQL error log (generated by default). To generate the slow-query and general logs, set the corresponding parameters in the DB parameter group.

You can view logs from the Amazon RDS console, the Amazon RDS API, the AWS CLI, or the AWS SDKs. You can also read log files with SQL through the `log_fdw` extension (available on Aurora 18) or with `aurora_log_report()` from `aurora_stat_utils`. The best long-term option is to **publish logs to CloudWatch Logs** (`--cloudwatch-logs-export-configuration '{"EnableLogTypes":["postgresql"]}'`) for search, retention, metric filters and alarms. (The playbook's "binary logs" sentence refers to MySQL and does not apply to PostgreSQL.)

Parameters controlling log/error file placement (modify via an Aurora DB Parameter Group):

| Parameter | Description |
|---|---|
| `log_filename` | File name pattern for log files. |
| `log_rotation_age` | (min) Rotate log file after N minutes. |
| `log_rotation_size` | (kB) Rotate log file after N kilobytes. |
| `log_min_messages` | Message levels that are logged (`DEBUG`, `ERROR`, `INFO`, …). |
| `log_min_error_statement` | Log all statements generating errors at or above this level. |
| `log_min_duration_statement` | Minimum run time (ms) above which statements are logged. |

Example — view the Aurora PostgreSQL error log in the RDS console:
1. In the AWS console, choose **RDS** → **Databases**.
2. Choose the instance whose error log you want.
3. Scroll to the logs section and choose the log name; the log viewer displays its content.

## Conversion notes

- AWS service replacement: access logs via the Amazon RDS console / API / AWS CLI / SDKs instead of the SSMS Log Viewer and Windows Application Log.
- Slow-query and general logs are not on by default — enable them through DB parameter groups.
- Logs can be read with SQL (`log_fdw`) or exported to CloudWatch Logs.
- `log_destination` allows `stderr` or `csvlog` on Aurora 18 (no `jsonlog`). PostgreSQL 18's `log_connections` takes a list (`receipt,authentication,authorization,setup_durations` or `all`). Add `log_lock_waits = on`, `log_temp_files = 0`, and `log_autovacuum_min_duration` to get information SQL Server DBAs expect from the error log.
- SQL Server error numbers in the table above map to SQLSTATEs (for example login failed 18456 → `28P01`, duplicate key 2627 → `23505`) and Aurora events (storage full → RDS event notification).
