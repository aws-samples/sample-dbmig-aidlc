# Target baseline — Aurora PostgreSQL 18 for SQL Server sources

> **Validated on:** Aurora PostgreSQL **18.6** and SQL Server 2022 (RDS, 16.0.4295.3), 2026-10-30,
> with direct driver connections (psycopg, python-tds). "Verified" means the statement was run on both.
> Platform facts shared with the Oracle pair (extensions, parameters, instance classes, DMS, Database
> Insights) are in `../../oracle-to-postgresql-playbook/references/target-baseline-aurora-postgresql-18.md`.

The original AWS playbook was written for Aurora PostgreSQL 10–13. Target the latest major version (18).
This file lists the conversion defaults that follow from it and the behaviour differences that change
results without an error. Topic files carry the details.

## Conversion defaults on PostgreSQL 18 (supersede older playbook advice)

| SQL Server construct | PG 18 default | Topic file |
|---|---|---|
| `MERGE` (incl. `WHEN NOT MATCHED BY SOURCE`, `OUTPUT $action`) | native `MERGE` with `WHEN NOT MATCHED BY SOURCE` and `RETURNING merge_action()` (PG 17+, verified) | `tsql/merge.md` |
| `IDENTITY` | `GENERATED BY DEFAULT AS IDENTITY`; `SET IDENTITY_INSERT ON` → `INSERT … OVERRIDING SYSTEM VALUE` (verified); reseed after load (`dbmig reset-identity`) | `tsql/identity-and-sequences.md` |
| Procedure returning a result set | `CREATE FUNCTION … RETURNS TABLE` (callers `SELECT * FROM f()`); a `CREATE PROCEDURE` cannot return rows | `tsql/stored-procedures.md` |
| Procedure with `OUTPUT` params | `CREATE PROCEDURE` with `OUT`/`INOUT` (PG 14+); callers in PL/pgSQL pass variables | `tsql/stored-procedures.md` |
| `TRY/CATCH`, `THROW`, `RAISERROR`, `ERROR_*()` | `BEGIN … EXCEPTION`, `RAISE`, `GET STACKED DIAGNOSTICS` (pass values to nested loggers) | `tsql/error-handling.md` |
| `CROSS/OUTER APPLY` | `CROSS JOIN LATERAL` / `LEFT JOIN LATERAL … ON true` | `ansi-sql/table-join.md` |
| `TOP n [WITH TIES]`, `OFFSET … FETCH` | `LIMIT n` / `FETCH FIRST n ROWS WITH TIES` (verified) | `tsql/top-fetch.md` |
| `TRY_CAST`/`TRY_CONVERT` | `CASE WHEN pg_input_is_valid(v, 'integer') THEN v::int END` (PG 16+, verified) | `tsql/cast-and-convert.md` |
| `STRING_SPLIT(s, d, 1)` | `string_to_table(s, d) WITH ORDINALITY` (verified) | `tsql/string-functions.md` |
| `STRING_AGG … WITHIN GROUP (ORDER BY …)` | `string_agg(v, d ORDER BY …)` (verified) | `tsql/string-functions.md` |
| `JSON_VALUE`, `JSON_QUERY`, `OPENJSON` | SQL/JSON `JSON_VALUE … RETURNING`, `JSON_QUERY`, `JSON_TABLE` (PG 16/17, verified for `JSON_VALUE`) | `tsql/json-and-xml.md` |
| `NEWID()` / `NEWSEQUENTIALID()` | `gen_random_uuid()` / `uuidv7()` (time-ordered, PG 18, verified) | `ansi-sql/data-types.md` |
| Computed column (non-persisted / `PERSISTED`) | `GENERATED ALWAYS AS (…) VIRTUAL` (PG 18 default) / `STORED`. Virtual columns **cannot be indexed** (verified) — use `STORED` when the SQL Server column is indexed | `ansi-sql/creating-tables.md` |
| `UNIQUE` index allowing one `NULL` | `UNIQUE NULLS NOT DISTINCT` (PG 15+, verified) — a plain PG `UNIQUE` accepts many NULLs | `ansi-sql/constraints.md` |
| `…_CI_AS` collations | `citext`, or an ICU nondeterministic collation (`=` and `LIKE` are case-insensitive on PG 18, `ILIKE` is not supported with it — verified); or `lower()` / `ILIKE` at the call sites | `tsql/collations.md` |
| Linked servers | `tds_fdw` 2.0.5 (available on Aurora 18.6) or `postgres_fdw` | `management/linked-servers.md` |
| SQL Agent jobs | `pg_cron` / EventBridge Scheduler | `management/sql-server-agent.md` |

## Behavior differences to test for (verified on SQL Server 2022 and PG 18.6)

- **Case and trailing spaces:** under `SQL_Latin1_General_CP1_CI_AS`, `'abc' = 'ABC'` and `'a ' = 'a'` are
  true; in PostgreSQL both are false for `varchar`/`text` (`char(n)` ignores trailing spaces).
- `LEN('ab  ')` = 2 (ignores trailing spaces); PostgreSQL `length('ab  ')` = 4. `DATALENGTH(N'ab')` = 4
  (UTF-16) vs `octet_length('ab')` = 2.
- `CAST('' AS int)` = 0; PostgreSQL `''::int` raises `invalid input syntax`.
- `CAST(2.5 AS int)` = 2 and `CAST(-2.5 AS int)` = -2 (truncation); PostgreSQL `2.5::int` = 3 (rounds).
  `ROUND(CAST(2.5 AS float), 0)` = 3; PostgreSQL `round(2.5::float8)` = 2 (banker's rounding on float).
- `DATEDIFF(month, '2024-01-31', '2024-02-01')` = 1 (boundaries crossed); an `age()`-based rewrite gives 0.
  `DATEDIFF(day, …)` counts midnights: use `d2::date - d1::date`.
- `datetime` rounds to 1/300 s (`.002` → `.003`); `timestamp(3)` keeps `.002`.
- `NULL` sorts **first** ascending in SQL Server, **last** in PostgreSQL — add `NULLS FIRST` where order matters.
- A `UNIQUE` index allows one `NULL` in SQL Server and many in PostgreSQL (use `NULLS NOT DISTINCT`).
- `'a' + NULL` is NULL in both (`CONCAT_NULL_YIELDS_NULL ON`); `CONCAT` skips NULLs in both. Integer `/` and
  `%` agree (`-7/2` = -3, `7 % -3` = 1); division by zero raises in both.
- `IIF(NULL = NULL, …)` is false in both; `GREATEST(1, NULL, 3)` = 3 in both (SQL Server 2022+).
- `now()` / `CURRENT_TIMESTAMP` are fixed at transaction start (verified on 18.6); `GETDATE()` is evaluated per
  statement (documented) — use `clock_timestamp()` where code measures elapsed time inside a transaction.
- A procedure with its own `BEGIN TRAN`/`COMMIT` must keep transaction control out of functions; PL/pgSQL
  `COMMIT` fails inside a block with an `EXCEPTION` clause.
