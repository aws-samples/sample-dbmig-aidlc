# Oracle Identity Columns and PostgreSQL SERIAL Type

> Source: AWS Oracle→Aurora PostgreSQL Migration Playbook
> URL: https://docs.aws.amazon.com/dms/latest/oracle-to-aurora-postgresql-migration-playbook/chap-oracle-aurora-pg.sql.identity.html

**Conversion category:** Assisted (Four-star feature compatibility, three-star automation; since PostgreSQL 10 the only differences are data types)
**SCT automation:** Three-star automation level; SCT action code index → Sequences

> **Reviewed for Aurora PostgreSQL 18** (validated on 18.6, 2026-10-29): identity over SERIAL, no `ON NULL` equivalent (verified), `OVERRIDING SYSTEM VALUE` for loads (verified), PG 17 identity on partitioned tables, `RESTART`/`setval` reset and `dbmig reset-identity`.

## Oracle

Oracle 12c introduced automatic value generation for columns. The `IDENTITY` type creates a sequence and associates it with a table column without a separate sequence object. Internally it relies on sequences, which can also be configured manually.

```sql
CREATE TABLE IDENTITY_TST (
  COL1 NUMBER GENERATED BY DEFAULT AS IDENTITY(START WITH 100 INCREMENT BY 10),
  COL2 VARCHAR2(30));

INSERT INTO IDENTITY_TST(COL2) VALUES('A');
INSERT INTO IDENTITY_TST(COL1, COL2) VALUES(DEFAULT, 'B');
INSERT INTO IDENTITY_TST(col1, col2) VALUES(NULL, 'C');
SELECT * FROM IDENTITY_TST;

COL1   COL2
---    ---
100    A
110    B
```

## PostgreSQL

PostgreSQL offers two approaches:

1. **`SERIAL` pseudo-type** (`SMALLSERIAL`, `SERIAL`, `BIGSERIAL`): creates a sequence implicitly using default configuration and adds a `NOT NULL` constraint. The sequence can be altered like any other.

```sql
CREATE TABLE SERIAL_SEQ_TST(COL1 SERIAL PRIMARY KEY, COL2 VARCHAR(10));

ALTER SEQUENCE SERIAL_SEQ_TST_COL1_SEQ RESTART WITH 100 INCREMENT BY 10;
INSERT INTO SERIAL_SEQ_TST(COL2) VALUES('A');
INSERT INTO SERIAL_SEQ_TST(COL1, COL2) VALUES(DEFAULT, 'B');
SELECT * FROM SERIAL_SEQ_TST;
```

2. **Identity columns** (PostgreSQL 10+): more SQL-standard compliant and highly compatible with Oracle identity columns. This form is Oracle-compatible:

```sql
CREATE TABLE emps (
emp_id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
emp_name VARCHAR(35) NOT NULL);

INSERT INTO emps (emp_name) VALUES ('Robert');
INSERT INTO emps (emp_id, emp_name) VALUES (DEFAULT, 'Brian');
```

## Conversion notes

- Prefer **identity columns** over `SERIAL` (now a legacy convenience): the sequence is owned by the column, permissions follow the table, and `ALTER TABLE … ALTER COLUMN … RESTART` works. Map Oracle `GENERATED ALWAYS` → `GENERATED ALWAYS`, and `GENERATED BY DEFAULT` → `GENERATED BY DEFAULT`.
- Oracle `GENERATED BY DEFAULT **ON NULL**` has no PostgreSQL clause. Inserting an explicit NULL into an identity column fails with `23502` (verified). If the application inserts NULL to mean "generate", add a `BEFORE INSERT` trigger that sets `NEW.id := nextval(pg_get_serial_sequence('t','id'))` when it is NULL.
- `GENERATED ALWAYS` rejects explicit values (`428C9`, verified). Data loads must use `INSERT … OVERRIDING SYSTEM VALUE` (DMS and `COPY` handle this), or the column must be `BY DEFAULT` during migration.
- Identity columns on **partitioned tables** are supported since PG 17 (verified on 18.6).
- Use `bigint` for identity columns converted from `NUMBER` keys unless the range is known to fit `integer`.
- In both PG `SERIAL` and `IDENTITY`, you can insert explicit values that don't violate the PK. Doing so without advancing the sequence later causes a duplicate-key error when the sequence catches up:
  ```
  SQL Error [23505]: ERROR: duplicate key value violates unique constraint "emps_iden_pkey"
  Detail: Key (emp_id)=(2) already exists.
  ```
  After bulk loads with explicit IDs, reset the sequence: `SELECT setval(pg_get_serial_sequence('t','id'), (SELECT COALESCE(max(id), 0) + 1 FROM t), false);` or `ALTER TABLE t ALTER COLUMN id RESTART WITH <n>;` (verified). In this toolkit, `./dbmig reset-identity --schema <S> --project <P> [--apply]` does this for every identity column at cutover.
- The main residual difference is the underlying numeric data type (NUMBER vs INTEGER/BIGINT).
