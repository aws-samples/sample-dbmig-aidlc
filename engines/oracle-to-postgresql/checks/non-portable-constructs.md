# Non-portable Oracle → PostgreSQL constructs (field-tested checklist)

Patterns with **no direct PostgreSQL equivalent** and how to convert them, distilled from real
Oracle→Aurora PostgreSQL runs (the `DEMO` schema). Each item: the Oracle construct, the failure if
converted naively, and the recommended conversion. The construction skill injects this file as
context, so keep it prescriptive.

## Datatypes

- **`NUMBER(19,0)` (and larger) as an IDENTITY/PK** → `bigint GENERATED BY DEFAULT AS IDENTITY`.
  Do **not** map an identity/PK to `numeric`: PostgreSQL `GENERATED … AS IDENTITY` requires an
  integer type (`smallint`/`integer`/`bigint`). Reserve `numeric(p,s)` for non-key columns.
- **`NUMBER(1,0)` boolean-style flags** → `smallint` + `CHECK (col IN (0,1))`, not `boolean`, when the
  application stores/compares `0/1` and the data is copied verbatim. Only map to `boolean` if the app
  and all queries are updated. Keeping `smallint` avoids a data-copy type mismatch.
- **`DATE`** → `timestamp(0)`, **not** `date`. Oracle `DATE` carries a time-of-day component; mapping to
  `date` silently truncates it.
- **`NUMBER(10,0)`** → `bigint` (10 digits exceed `int32`), not `integer`.
- **`BLOB`** → `bytea`; **`CLOB`/`NCLOB`** → `text`. `bytea` has a practical ~1 GB limit — check very
  large objects.

## Sequences / identity

- Oracle `GENERATED … AS IDENTITY (START WITH n …)` → PostgreSQL identity with `(START WITH n)`.
  After a data load that supplied explicit key values, **advance the identity** to `MAX(key)` (the
  toolkit's `reset_identity` does this) or the next app insert collides.

## Indexes

- **PK-implicit unique indexes (`SYS_C…`)**: Oracle lists a system unique index backing each PK. Do
  **not** re-create it in PostgreSQL — the `PRIMARY KEY` already creates its own unique index
  (duplicate → "relation already exists").
- **LOB indexes (`SYS_IL…`)** are internal; drop them (PostgreSQL TOAST manages `bytea`/`text`).
- **Oracle Text domain index** (`INDEXTYPE IS CTXSYS.CONTEXT`) → a **GIN full-text index**:
  `CREATE INDEX … USING gin (to_tsvector('english', coalesce(col, '')))`. Rewrite `CONTAINS()`
  predicates to `@@ to_tsquery(...)`.

## PL/SQL → PL/pgSQL

- **Packages** have no equivalent → flatten each subprogram to a schema-level routine
  `<package>_<subprogram>` (see `checks/package-naming.md` for collision handling).
- **`PIPELINED` table functions** (`RETURN … PIPELINED` / `PIPE ROW`) → a set-returning function
  `RETURNS TABLE(...)` with `RETURN QUERY`.
- **`SELECT … INTO`** raises `NO_DATA_FOUND` in Oracle; plain PL/pgSQL `SELECT INTO` does **not**. Use
  `SELECT … INTO STRICT` (raises `NO_DATA_FOUND`/`TOO_MANY_ROWS`) when the Oracle code relied on it.
- **`DETERMINISTIC`** → `IMMUTABLE`; `PARALLEL_ENABLE` → `PARALLEL SAFE`.
- **Function/expression mapping**: `NVL`→`COALESCE`, `SYSDATE`/`SYSTIMESTAMP`→`now()`,
  `DBMS_OUTPUT.PUT_LINE`→`RAISE NOTICE`, `RAISE_APPLICATION_ERROR`→`RAISE EXCEPTION`,
  `SQL%ROWCOUNT`→`GET DIAGNOSTICS x = ROW_COUNT`, `FETCH FIRST n ROWS ONLY`→`LIMIT n`,
  `TRUNC(date)`→`col::date`, `REGEXP_LIKE(x,p)`→`x ~ p`.
- **`REGEXP_REPLACE`** replaces **all** matches in Oracle; PostgreSQL replaces only the first unless the
  **`'g'`** flag is given — add it (`regexp_replace(x, p, r, 'g')`).
- **`DELETE FROM (subquery)`** (Oracle inline-view delete) → a direct `DELETE FROM t WHERE …`.

## Transactions in procedures (testability)

- Oracle procedures often end with **`COMMIT`**. Prefer **removing** the explicit `COMMIT` and letting
  the caller own the transaction (PostgreSQL idiom). This is also required for the equivalence harness:
  `run-tests` wraps each case in a transaction and rolls it back, so a procedure that `COMMIT`s against
  the **live source** persists the change (and breaks repeatability). Mutating procedures that must keep
  a `COMMIT` are not net-effect testable via the harness — test them against a non-existent key or flag
  for manual review.

## Triggers

- Oracle row triggers with inline bodies → a PL/pgSQL trigger **function** + a `CREATE TRIGGER` binding.
  A `BEFORE INSERT/UPDATE` trigger that derives a column (e.g. a search string) maps cleanly to setting
  `NEW.col`. Foreign keys **and** triggers should be applied **after** the data load (`--post-data`) so
  they neither force load order nor rewrite the rows being loaded.
