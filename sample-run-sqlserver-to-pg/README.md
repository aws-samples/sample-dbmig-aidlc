# Sample run — SQL Server AdventureWorks (`Person` + `HumanResources`) → Aurora PostgreSQL

A complete, real end-to-end migration captured for reference. Every file here was produced by the
`dbmig` toolkit and the Kiro-driven conversion during an actual run against live databases.

## What was migrated

| | |
|---|---|
| **Source** | Amazon RDS for SQL Server 2022, database `AdventureWorks` |
| **Target** | Amazon Aurora PostgreSQL 17.7 — a **new database `adventureworks`** created for this run |
| **Scope** | Schemas **`Person`** + **`HumanResources`** — a self-contained set (`HumanResources` depends only on `Person`) |
| **Region / profile** | `us-east-1` (workshop account) |
| **Project workspace** | `migrations/adventureworks/` (archived verbatim into this folder) |
| **Credentials** | AWS Secrets Manager (`MMA-secret-sqlserver-admin`, `MMA-secret-aurora-admin`), injected as env vars at run time — never written to any artifact here |

**Objects:** 19 tables (Person 13, HR 6), 8 views (Person 2, HR 6), 3 stored procedures, 2 triggers.

## Result at a glance

- **Schema**: Person 13/13 + HR 6/6 tables applied (pre-data); deferred FKs + triggers applied post-data (Person 8/8, HR 4/4, including the cross-schema `employee → person` FK).
- **Code**: 11/11 objects applied (2 Person views, 6 HR views, 3 HR procedures).
- **Data**: **142,184 rows** reconciled (Person 141,250 across 13 tables, HR 934 across 6).
  Of these, the framework's `migrate-data` copied 122,280 (Person 121,636 / HR 644); the two
  binary-typed tables — `Person.Address` (19,614) and `HumanResources.Employee` (290) — were
  **custom-loaded** with source-side `STAsText()`/`ToString()` conversion (see the notes below),
  so they don't appear in `data/migrate_report-*.yaml` but are counted in the reconcile totals.
- **Reconciliation**: **19/19 tables match** on row count.
- **Equivalence tests**: **13/13 pass** (Person 3/3, HumanResources 10/10).

## Notable conversion decisions (SQL Server → PostgreSQL)

**Datatypes**
- `int IDENTITY(1,1)` → `integer GENERATED BY DEFAULT AS IDENTITY` (`smallint`/`tinyint` identities kept as `smallint`).
- `nvarchar/nchar` → `varchar/char`; `datetime` → `timestamp`; `bit` → `boolean`; `money` → `numeric(19,4)`;
  `tinyint` → `smallint`; `time` → `time`; `uniqueidentifier` → `uuid` (`newid()` → `gen_random_uuid()`); `xml` → `xml`.
- User-defined types (`Name`, `Flag`, `NameStyle`, `Phone`, `AccountNumber`, `OrderNumber`) → their base types.
- `getdate()` defaults → `now()`.

**Hard constructs**
- **`hierarchyid`** (`Employee.OrganizationNode`) → `text` storing the path string (`/1/1/`). Since generic COPY
  returns the opaque binary, this column is **custom-loaded** using the source expression `OrganizationNode.ToString()`.
- **`geography`** (`Address.SpatialLocation`) → `text` (WKT), **custom-loaded** via `SpatialLocation.STAsText()`
  (PostGIS is available on the target if a spatial type is preferred).
- **Computed column** `Employee.OrganizationLevel` → a plain `smallint` loaded from the source value.
- **XML-shredding views** (`vAdditionalContactInfo`, `vJobCandidate`, `vJobCandidateEducation`,
  `vJobCandidateEmployment`): SQL Server `.nodes()/.value()` with XML namespaces → PostgreSQL `xpath()` and
  `LATERAL unnest(xpath(...))`, with a namespace map (`CROSS APPLY` → `LATERAL`). Dotted element names
  (`Name.First`, `Edu.Level`, …) preserved as quoted output columns.
- **Triggers**: `iuPerson` (AFTER INSERT/UPDATE defaulting the Demographics survey XML) → a PL/pgSQL BEFORE
  trigger (the XML `.modify()` "insert node if missing" branch is simplified to the NULL-default case);
  `dEmployee` (SQL Server `INSTEAD OF DELETE` blocking deletes — not allowed on tables in PostgreSQL) →
  a `BEFORE DELETE` trigger that raises an exception.
- **Stored procedures** (`uspUpdateEmployee*`): T-SQL `TRY/CATCH` → PL/pgSQL `EXCEPTION`; the source logs and
  continues via `dbo.uspLogError` (out of scope), so the handler is converted to **swallow-and-log**
  (`RAISE WARNING`) to preserve the observable "log and continue" behavior; `money`→`numeric`,
  `hierarchyid` param → `text`.
- **CHECK constraints** referencing `getdate()` (`CK_Employee_BirthDate`, `CK_Employee_HireDate`) are reduced to
  their **static bounds** — PostgreSQL requires CHECK expressions to be IMMUTABLE.

**Out-of-scope trim**
- The single cross-schema FK `Person.StateProvince.TerritoryID → Sales.SalesTerritory` is **dropped** (Sales is
  out of scope); `territoryid` is retained as a plain column.

## Lessons worth keeping

1. **Spatial/hierarchical columns need source-side text conversion.** `hierarchyid` and `geography` come back as
   opaque binary through the generic driver path, so those two tables (`Employee`, `Address`) were excluded from
   the generic `migrate-data` (`--tables` include lists) and **custom-loaded** with `OrganizationNode.ToString()`
   / `SpatialLocation.STAsText()`. Everything else migrated through the framework unchanged.
2. **Procedures with explicit T-SQL transaction control can't be net-effect tested via the rollback harness.**
   `uspUpdateEmployeeHireInfo` wraps its work in `BEGIN TRANSACTION … COMMIT` with `ROLLBACK` in `CATCH`; inside
   the harness's own transaction this trips SQL Server error 266 (transaction-count mismatch), and the COMMIT
   path would persist to the source. It is documented and excluded from equivalence execution (its converted DDL
   still applies cleanly). The other two procedures have no explicit COMMIT, so the harness safely rolls them back
   and they are tested against a real employee.
3. **Passing a `hierarchyid` argument to an `EXEC` needs a declared variable** (`DECLARE @o hierarchyid =
   hierarchyid::Parse(N'/2/')`) — an inline `CAST(...)` is rejected as an `EXEC` parameter.

## Reproducing

With `connections.yaml`/`migration-config.yaml` pointed at your endpoints (see the masked
`sample_connections.yaml`) and `SQLSERVER_PASSWORD`/`PG_PASSWORD` exported from your secret store, run
`inventory → convert-schema → apply-schema → convert-code → apply-schema --code → migrate-data →
apply-schema --post-data → compare → gen-tests → run-tests` for each schema (`--schema Person`, then
`--schema HumanResources`). The two binary-typed tables (`Person.Address`, `HumanResources.Employee`) are
loaded with a small custom step that converts `geography`/`hierarchyid` to text at the source. The target
database `adventureworks` was created once up front with `CREATE DATABASE adventureworks`.
