# Migration Plan — DEMO (Oracle 19c → Aurora PostgreSQL 17.7)

## 1. Scope
**In:** Oracle schema `DEMO` → target schema `demo` in `demodb`. 14 user tables, integer IDENTITY PKs,
constraints, real secondary indexes, 12 sequences (as identity), 5 functions, 5 procedures, 5 packages
(flattened), 1 trigger. Strategy `full` (schema + **all** data, 199 rows).

**Out / not migrated:** Oracle Text `DR$BOOKS_TEXT_IDX$*` internal tables and system indexes
(`SYS_C*`, `SYS_IL*`) — replaced by native PG equivalents, not copied. No views (none exist).

**Identifier case:** fold Oracle UPPER → PostgreSQL lower, unquoted.

## 2. Conversion order (units of work)
Each unit converts and applies independently, tracing back to the inventory:

1. **Schema/objects DDL** — tables + columns + PK/UK/CHECK + real secondary indexes (FKs & triggers deferred).
   - IOT → heap + PK; BLOB → bytea; DATE → timestamp(0); IDENTITY → `bigint GENERATED BY DEFAULT AS IDENTITY`.
2. **Stored code** (`--code`) — functions → procedures → packages (flattened to `<pkg>_<subprogram>`).
3. **Full data load** — `migrate-data` (parallel COPY, PK-chunked); all 14 tables.
4. **Post-data** (`--post-data`) — foreign keys + the trigger (rewritten to PL/pgSQL), then **advance identities** to `MAX(id)`.
5. **Oracle Text redesign (Manual)** — add `GIN (to_tsvector('english', …))` on `BOOKS`; rewrite
   `TRG_BOOK_SEARCH_TEXT` to maintain the PG search/tsvector column. Flagged for explicit review.

## 3. Testing approach
- **Data path:** `framework` — `dbmig migrate-data` performs the one-time full load (dev/test scale).
- **Reconcile:** row counts (exact), per-column checksums, numeric aggregates, keyed sample — all 14 tables.
- **Equivalence tests (Kiro-generated from real data):**
  - Function parity (5) — same input → same return value.
  - Procedure parity (5) — same input → same net effect, run in a rolled-back transaction.
  - Assert known differences: empty-string/NULL, DATE→timestamp, numeric rounding.
- Full spec: `engines/oracle-to-postgresql/checks/equivalence-spec.md`.

## 4. Cutover approach (high level — detailed in Operations)
Small static dataset → single-shot cutover: apply schema+code, full load, apply post-data, reconcile,
validate, then repoint the app to Aurora. Rollback = keep Oracle authoritative until sign-off; target
schema is drop-and-recreate. Detailed cutover + rollback + monitoring produced in the Operations phase.

## 5. Open questions / decisions for the user
1. **Oracle Text (item 16):** confirm the search feature must be preserved in PostgreSQL (redesign to
   GIN full-text). If the app no longer needs in-DB full-text search, we can drop the index+trigger instead.
2. **Empty string vs NULL:** any app columns where Oracle `''`-as-NULL semantics are load-bearing? (None
   obvious in this schema — default handling assumed.)
3. **Target schema state:** `demo` will be created and objects applied into it. Confirm it's safe to
   create/replace objects in `demodb.demo` (destructive on re-runs).

## 6. Effort & risk summary
- **Automatic:** most tables, datatypes, constraints, secondary indexes, sequences, BLOB.
- **Assisted:** identity mapping, DATE mapping, IOT, all stored code (packages flattened) — ~450 PL/SQL lines.
- **Manual:** 1 item — Oracle Text index + trigger.
- **Blocked:** none.
- **Overall risk: LOW.** Tiny dataset, no cross-schema deps, single well-understood redesign. Primary
  effort is PL/SQL→PL/pgSQL conversion + the full-text redesign.
