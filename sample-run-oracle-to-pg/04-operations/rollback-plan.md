# Rollback plan — DEMO → demo

- **Point of no return:** the first application write accepted by Aurora (runbook step 8). Before it,
  roll back by re-pointing the app at Oracle (previous build + Oracle datasource) and lifting the write
  freeze — no data divergence.
- **Decision criteria:** any 5xx on the smoke paths, `ddl-auto=validate` failure, a reconcile mismatch,
  error rate > 2× the Oracle baseline, or p95 latency of `/books` > 2× baseline for 15 minutes.
- **After the point of no return:** writes exist only on Aurora. Either run AWS DMS reverse replication
  (Aurora → Oracle) from cutover, or export the rows created after cutover (`created_on > <cutover ts>`
  on orders, order_items, listings, customers, shopping_cart_items, password_reset_tokens) and replay
  them. Advance Oracle identities past the Aurora `MAX(id)` values first so replayed keys do not collide.
- **Aurora-side recovery:** restore the pre-cutover cluster snapshot or use point-in-time restore to a new
  cluster (Aurora PostgreSQL has no Backtrack — `ha-dr/flashback-database-and-snapshots.md`).
- Keep the Oracle source intact and reachable for a 14-day soak.
